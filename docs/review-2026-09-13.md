## 确认的问题

1. **[P1] 旧 daemon 的 launchd 任务没有被卸载。** `crates/core/src/service.rs:126` 使用 `bootout <domain> <label>`，但该形式的最后一个参数必须是 plist 路径；按 label 卸载应传单个 `<domain>/<label>`。返回码被忽略后，旧 socket 仍可连接，`start_locked` 在第 137 行直接成功返回，新任务并未接管；停止时旧 `KeepAlive` 任务也可能再次拉起进程。在独立的临时 launchd 任务上实测：当前参数形式退出码为 5，任务仍然存在；改用 service target 后退出码为 0，任务消失。另需覆盖自定义数据目录：`LABEL` 更名也改变了带 hash 的标签，而第 123 行会直接跳过这些旧任务。修复应识别对应数据目录的旧标签、检查卸载结果并完成接管，不能仅删除 plist。

2. **[P1] 升级后丢失原有登录启动偏好。** `crates/core/src/service.rs:127-131` 与 `tray/Sources/RemoventTray/StatusBarController.swift:535-544` 删除旧登录 plist，却没有先为新标签保留注册。daemon 的普通 `start` 只生成 run 目录的临时 plist；tray 则只有用户再次操作开关才创建新登录 plist。原本开启“登录时启动服务器 / 菜单栏”的用户，升级后这两项会变成关闭，下一次登录不再自动运行。应先迁移旧的开启状态，成功写入新注册后才移除旧注册，并保证重复启动幂等。

3. **[P1] 自定义目录的 tray 启动也会清理正式安装的登录项。** `tray/Sources/RemoventTray/StatusBarController.swift:63` 无条件调用迁移；第 536-541 行始终操作当前用户的 `com.removent.tray`，完全不检查 `REMOVENT_DATA_DIR`。因此运行 `scripts/dev.sh` 或使用临时目录的托盘测试，也会删除正式旧版本的登录设置。该调用发生在 IPC 连接之前，不能由测试 daemon 或其数据目录隔离。应根据有效数据目录和应用身份决定是否拥有该登录项，开发 / 临时实例不得清理系统标签。

4. **[P2] 编辑收藏的地址或账号会新增记录，原记录不变。** `ConnectionDialog::prefill` 只保留字段，没有保留 `saved.id`；`crates/app/src/engine.rs:538-540` 再次用 `from_request` 构造无 id 的记录，`crates/client/src/saved.rs:157` 仅按协议、主机、端口、用户名和 domain 查找。当这些字段任一改变时，产生新 id、旧收藏仍存在，UI 也仍选中旧项。独立 Rust 探针确认编辑 `old.local` → `new.local` 后条目数为 2，预期为 1。应让编辑路径携带稳定 id 并原位更新；新建路径仍可按端点去重，并明确定义编辑到已有端点时的处理。

5. **[P2] 重连时的时间戳刷新会覆盖新编辑，甚至恢复已删除记录。** `crates/app/src/engine.rs:563-565` 虽然重新读取磁盘，但随后将侧栏缓存的整条 `entry` 传给 `upsert`。另一个实例修改名称、账号状态或证书设置后，旧窗口重连会用旧字段覆盖磁盘；若其他实例已删除条目，`upsert` 又会插回该条目。探针先写入 `Edited`，再模拟旧窗口 touch，磁盘名称回到 `Original`。应按 id 仅更新 `last_used_unix`，条目不存在时不要插入，并在使用前刷新连接数据。

6. **[P2] 收藏文件的并发读改写会静默丢失数据。** `crates/client/src/saved.rs:152-172,176-193` 使用实例内快照进行整文件替换，`atomic_write` 只保证文件完整，没有将 load / mutation / flush 串成事务。应用没有对主进程使用 `DataDirLock`，因此多个实例可同时操作同一数据目录。两个 store 都加载空列表，A 保存一个收藏、B 再保存另一个，最终磁盘只有 B；独立探针得到 1 条，预期为 2。应在数据层为整个事务加跨进程锁，并在锁内读取最新状态，覆盖插入、编辑、删除和 touch。

7. **[P2] 钥匙串失败被当成保存成功，后续可能继续使用旧密码。** `crates/app/src/engine.rs:541-548` 忽略删除错误、仅记录存储错误，却仍返回成功；`password_hint` 已在调用钥匙串前持久化。如果已有旧密码且覆盖失败，之后钥匙串恢复可读时，`connect_saved` 读到旧密码就直接连接，不会像注释声称的那样回退到输入表单。清空密码但删除失败时，编辑入口又会无条件读取旧密码并预填。详情文案还断言密码已存入钥匙串。应区分“连接字段已保存”与“密码已保存”，显式呈现失败，避免将失效旧密码视为当前凭据，并测试写入、删除失败后的重试。

8. **[P2] 收藏保存失败的 UI 提示会立即被覆盖。** `crates/app/src/ui/home.rs:542-560` 在保存失败时设置警告，随后 `connect_request` 一旦成功排队，便在同一次事件处理中把 status 改成“正在连接”。用户即使遇到只读目录、磁盘写满等情况，也无法看到未保存提示。应让非阻断的保存警告独立保留，例如在表单或 toast 中显示；远程连接可以继续，但不能把未保存显示成成功。

## 发布兼容性与 UI 结论

`dfa67f5` 的提交说明已明确承认 bundle identifier 更名需要重装，这不是本次首次发现或非预期的代码行为。但它与“beta.4 用户可通过应用内更新到下一版”不兼容：beta.4 的 `release_codesign_requirement` 限定 `io.removent.app`，新包为 `com.alkinum.removent`，新二进制自身接受新标识也不能改变旧二进制的验证规则。若要求连续内置更新，应保留旧标识或设计旧标识签名的过渡发布；若选择手动重装，需在下一版安装说明中明确说明，并验证权限重新授权。不能仅修改新版本 updater 就宣称迁移已解决。

收藏的“编辑”入口复用了连接表单，唯一提交动作是“连接”：单纯重命名也会尝试发起会话，没有独立的“保存”。这是明确的交互限制，应提供保存动作，或至少把当前行为命名为“编辑并连接”。不应让用户为了修改离线设备名称而启动一次连接。

GPUI 现有测试覆盖新增名称字段之后的 860×600 最小窗口、Tab / Shift-Tab 焦点限制、页脚可见性、取消、重试及被其他弹窗遮挡后的焦点恢复，并已通过。中英文各有 246 个 key，无重复，key 集合一致；新增删除图标已注册。但这不是人工视觉验收：原生 UI 自动化读取 `/Applications/Removent.app` 连续返回 `timeoutReached`，无法完成当前构建在真实窗口中的明暗主题、长名称、多收藏滚动和交互检查。不能据此确认 UI 无缺陷。

## 补充：VNC 右键发送错误（已修复于工作区）

用户补充反馈 VNC 右键失效。检查发现 `crates/client/src/vnc/input.rs` 为 Apple `RFB 003.889` greeting 设置了单独的按键顺序：将内部右键 bit `0x02` 原样发送，而普通 type-5 PointerEvent 的右键应该是 `0x04`，中键才是 `0x02`。因此 Apple 连接上的右键与中键互换；普通 VNC 分支已做正确转换。这段错误在 `v0.1.0-beta.4` tag 中已经存在。

协议依据是 [RFC 6143 §7.5.5](https://www.rfc-editor.org/rfc/rfc6143.html#section-7.5.5)。作为互操作参考，[noVNC 的当前实现](https://github.com/novnc/noVNC/blob/master/core/rfb.js)也在支持 ARD 认证的同时使用统一的标准 PointerEvent 映射，并不根据 Apple greeting 改变按键顺序。

先新增真实 loopback TCP 回归测试，再修改生产逻辑。修复前，标准 greeting 分支通过，但 Apple greeting 的第一个右键包实测为 `[5, 2, 0, 10, 0, 20]`，预期 `[5, 4, 0, 10, 0, 20]`，测试失败。修复统一了内部到 RFB 的按键映射，并从输入发送路径移除 Apple 专用开关；Apple 认证、Session Select 和零尺寸 framebuffer 初始化仍保持原有处理。

修复后 `removent-client` 的 VNC 测试 26 项通过，`removent-app` 的 viewer 测试 5 项通过。覆盖标准 / Apple greeting 的实际网络报文、ARD type-30 认证后的右键、右键拖动、按住右键滚动、左右键组合与独立释放、中键，以及三种鼠标按键在性能面板上结束拖动后的释放。测试服务端故意不提供完整画面更新，确认输入发送不依赖画面完成。

`cargo fmt --all --check`、受影响的 app / client 全 target Clippy、`cargo build --locked -p removent-app` 和 `git diff --check` 均通过；构建仍有上文记录的依赖 future-incompatibility 提示。新的开发可执行文件为 `target/debug/removent`，本次没有替换 `/Applications` 中的安装版，也没有重新发布安装包。

此验证证明程序发出的右键消息符合协议，也验证了 GPUI 到内部输入消息的路径；尚未在用户实际连接的远端 Mac 上观察到右键菜单弹出，不能将模拟服务端测试等同于真实远端验收。
