# Tray, private relay and macOS unlock development verification

Scope: independent desktop/tray/daemon lifecycle, authenticated self-hosted Rust
relay for native RVP, and development paths for an already logged-in lock screen
and the logged-out LoginWindow. FileVault integration is outside the clarified
scope. The user has no interruptible test Mac and requested development first.

## Changes reviewed

- Tray startup uses a per-data-directory kernel lock and receives the same data
  directory as the desktop. Daemon status distinguishes the enabled switch from
  actual listener readiness and reports host/relay failures. Host and relay tasks
  belong to the daemon lifecycle, independently of desktop/tray lifetime.
- The Rust relay requires a pinned server certificate and separate host/client
  room credentials. It forwards encrypted native RVP packets through bounded
  QUIC DATAGRAM queues, with connection/authentication/resource limits. Linux
  systemd/container configurations and a separate Linux workflow are included.
- The opt-in Quartz capture backend and restricted LoginWindow agent are
  implemented. Administrator installation validates signed code and snapshots
  trusted devices into root-owned storage. Ownership, mode, symlink and extended
  ACL checks cover executable/data ancestors. Plist publication is atomic, and
  publication failure rolls back the new bundle without replacing another agent.
- LoginWindow cannot initiate pairing or capability-expansion prompts. Admission
  excludes unavailable audio/clipboard/file capabilities, rejects unapproved
  video/input immediately, and rechecks current grants when resuming a session.
  Requests omitting video are rejected because this host always sends a video
  stream; omitting the request bit cannot bypass the stored video grant.

## Acceptance boundaries

The benchmark is a single-controller loopback transport measurement, excluding
screen capture, encoding, display and WAN conditions. A production VPS and Docker
runtime were unavailable; Linux cross-compilation does not substitute for live
deployment or concurrent-session measurements. Ordinary Cloudflare Workers and
orange-cloud HTTP proxying cannot expose this UDP listener; use a DNS-only VPS
record or a suitable Spectrum UDP origin.

No signed LoginWindow installation, TCC approval, real lock/password entry,
logout/login handoff or reboot acceptance was performed. The developer's Mac was
not locked, logged out or rebooted. The login-window path currently uses an
explicit administrator installation and separately managed trust snapshot;
ordinary tray sharing/revocation controls do not manage that snapshot. A unified
product installation/trust-management flow remains separate from this validation
path. Do not describe reliable unlock as verified before real-Mac acceptance.

Deployment and acceptance procedures:
[private relay](private-relay.md), [macOS unlock](macos-unlock.md).

The subsequent Cloudflare Containers extension adds WSS and a durable on-demand
control plane. Its implementation, separate measurements and validation boundary

## Add Host relay selection and three-party trust

The desktop now saves an explicit relay route per host: scheme/address/port,
room, relay certificate pin for QUIC, and a mandatory target host certificate
fingerprint. WSS uses normal CA/hostname validation. Relay credentials are
optional in the form and stored via the existing versioned Keychain transaction,
never in bookmark JSON. Saved relay routes can be selected again; credentials
are reused only within the same room and cleared after endpoint/pin/room edits.
Keychain selection reads run off the UI thread with stale-result guards.

The current relay wire implementation (now identified as v1) requires an Ed25519 proof of a fresh, room/role-bound challenge on
both QUIC and WebSocket connections. A room role must configure a credential hash
or registered public keys. When both are configured, both must match. Empty
credentials never enable anonymous access. The Cloudflare edge additionally
checks audience/time/nonce-bound admission signatures; its DO atomically stores
a bounded replay ledger before a controller can wake the container. The inner
RVP session requires the exact target host pin, including resume. Relay admission
cannot substitute for native pairing, controller grants or macOS permissions.

## Initial v1 baseline and beta cleanup

The user's clarification keeps the current implementation and security checks,
using v1 as the initial public protocol identifier. It is not a restoration of
an earlier implementation. Public addresses are `removent://host:port`; the
Cloudflare / HTTPS and VPS / QUIC carriers are selected separately. The same
parser is used by the desktop, CLI and daemon relay profiles. Only the current
v1 ALPN, WebSocket subprotocol and signature domains are accepted. Older URL
schemes and profile aliases have no compatibility fallback. Switching the
carrier clears its credential and QUIC pin; saved routes retain their carrier.

The application version is `0.1.0` (release preparation only). The beta update
feed, old bookmark secret-account fallback and pre-rename background-service
migration were removed. Stable update signatures, hashes, code signatures and
current service ownership checks are retained. Historical review documents are
kept as evidence, not as current compatibility requirements.

## Interactive deployment and source-network allowlists

Added `scripts/deploy_relay.sh` with configure/deploy/start/stop/status/logs for
Linux VPS/QUIC and Cloudflare Containers. `scripts/relay_setup.py` validates and
renders private JSON settings/credentials, daemon/controller TOML profiles,
Compose and Wrangler files. Blank first-use credentials generate independent
256-bit values; reconfiguration preserves them unless explicitly rotated.
Server/container files receive only hashes. Deployed Cloudflare admin credentials
are snapshotted so rotation can stop existing tunnels before applying changes;
post-deployment admission is explicitly stopped. Named Docker volumes preserve
relay certificate identity.

Rust checks bounded IPv4/IPv6 CIDRs against socket source addresses before
authentication. QUIC IP migration is disabled to prevent changing source networks
after admission. The Worker checks only the platform's CF-Connecting-IP at its
public ingress, before DO access. Restricted ingress rejects Worker subrequests,
missing/invalid sources and ignores user forwarding/extra IPv6 headers. Admin
CIDRs can be separate, unrestricted or inherit the tunnel policy. Matching and
parsing do not run in the media-packet forwarding loop.
